# Design language and UI (spartan + the jig-design skill)

Read this before you build UI, style a component, or make a mock. The **design language** is one thing with two homes, and confusing them is a DRY violation.

## The rule: two homes, one language

| You are building | Source of truth |
|---|---|
| **Production UI** (a real Angular view or control) | spartan helm components + the tokens in `frontend/src/styles.css` |
| **A mock, preview, slide, or throwaway prototype** | the `jig-design` skill (portable CSS/React, no Angular build) |

Both render the same visual language. They are not two design systems — the `jig-design` skill is a **faithful reproduction of the real frontend**, translated from Tailwind/spartan into standalone CSS so previews render pixel-accurate without a build. The app is upstream; the skill mirrors it. When the two disagree, `frontend/src/styles.css` and `frontend/libs/ui/*` win. See ADR 0007.

## Production UI

- **Controls are spartan helm.** Compose from `frontend/libs/ui/*` behind the `@spartan-ng/helm/*` alias; add one with `ng g @spartan-ng/cli:ui <name>`. Never hand-roll a styled control that spartan already provides. The `spartan` skill and MCP carry the component APIs.
- **Layout is Grid. Flex is for inline runs.** Anything that arranges a component's *regions* — a page, a view, a card's internal structure, a form's rows, a two-pane split — is `grid`, declared in one place with `grid-template-columns` / `grid-template-areas`. Flex is for a single inline run of content: an icon beside a label, a row of buttons, a list of chips. One axis, content-sized, order-driven.
  **The test:** if you are nesting a flex container inside another flex container to place things in two dimensions, that is a grid you have not written yet. Nested flex hides the layout in three files; a grid states it in one line you can read. The app shell in `frontend/src/app/shell/shell.layout.css` is the worked example — its whole structure is four lines of `grid-template-areas`.
- **Never hardcode a token.** Colors, radius, and shadow come from the CSS custom properties in `styles.css` (`--primary`, `--muted-foreground`, `--border`, `--radius`, `--sidebar`, …). A literal hex or px in a component is the smell.
- **Know which half of the look is a token and which is generated.** Color and radius are token-driven — the generated components reference `bg-primary` and `rounded-lg`/`rounded-sm`, so `styles.css` controls them and a change is one line (`--radius` derives `--radius-sm` at 0.6×, `--radius-md` at 0.8×, `--radius-lg` at 1×, and `--radius-xl` at 1.4×). Control *size and spacing* is not: the spartan style inlines literals (`h-8`, `px-2.5`, `gap-1.5`) into `libs/ui` at generation time, so making controls taller or roomier means `npm run ui:style -- <style>` and a regeneration, never a token edit. App-authored spacing has its own token scale instead (ADR 0011). Reaching for a token to change a height is the tell that you have the wrong lever. See ADR 0010.
- **Do not copy the skill's CSS into production.** The skill's `css/*` is a mirror for offline rendering; forking it into the app creates a second source of truth for the theme. Change the theme in `styles.css`; the skill is downstream.

## Mocks, previews, and prototypes

- **Invoke the `jig-design` skill.** It ships the tokens, component classes, the React primitives, and the app-shell / centered layouts, plus foundation specimen cards. Link its `styles.css` (one import) and build static HTML or React — no Angular, no Tailwind build required.
- **Prototype output stays out of production paths.** A mock is a throwaway artifact for the user to view, not code that ships. Promote it by rebuilding in spartan + `styles.css`, not by wiring the skill's bundle into the app.

## The non-negotiable feel

This section used to read as one list in one voice. It governed two codebases with different rules — app-authored code, which a gate can enforce, and `frontend/libs/ui`, generated by spartan and reasserted byte-for-byte by every `npm run ui:style` (ADR 0010) — and the single voice hid which claims were which. A 2026-09 audit checked every claim below against the running repo and found seven of eleven false, self-contradictory, or true only through an inheritance nobody had named. That audit is why the section is now two lists: what jig's own gates enforce, and what the vendored kit happens to look like today and may not tomorrow. Every claim in both lists is either gated — named — or explicitly marked a review rule with no exit code. There is no third category; an ungated, unmarked claim is exactly the defect the audit found.

The canonical statement of the visual language, with rationale, specimens, and dark mode, lives in the `jig-design` skill's readme and `foundations/`. What follows is what actually holds in this repo, checked, not the aspirational version.

### App-authored rules — enforced, and true

These bind `frontend/src/app` and are backed by a gate that fails the build or the commit. `frontend/libs/ui` is out of scope for all of them — see the vendored-kit facts below for what governs there instead.

- **Palette:** pure neutral OKLCH grayscale, zero chroma, everywhere in `styles.css` except one token. `--destructive` (red, `oklch(0.577 0.245 27.325)` light / `oklch(0.704 0.191 22.216)` dark) is the *only* chromatic token in the app. This is a review rule with no exit code, not a gate: `frontend/src/styles.css`, where the palette lives, is excluded from the Stylelint run entirely (see the `--ignore-pattern` in the root `package.json` `stylelint` script), and even where Stylelint does run, `scale-unlimited/declaration-strict-value` only checks whether a value is a `var()` reference — it cannot detect chroma, so `--brand: oklch(0.6 0.2 250)` would pass unflagged. What Stylelint does gate is a hardcoded color value in other authored component CSS; the zero-chroma property of the palette itself has no gate behind it today. `jig/no-raw-palette-color`, forbidding a raw Tailwind palette class (`bg-blue-500`, `text-gray-700`) in a template, lands in a later branch and is not yet wired.
- **Spacing:** a six-step scale on a 4px grid — `xs` 4px, `s` 8px, `m` 12px, `l` 16px, `xl` 24px, `2xl` 32px — declared as Tailwind `@theme` tokens in `styles.css` so each step is a real utility (`gap-m`, `px-l`, `mt-xs`). Gated by `jig/no-literal-spacing` (Angular templates) and Stylelint's `scale-unlimited/declaration-strict-value` on `padding`, `margin`, and `gap` (authored CSS). See ADR 0011 for why a token alone does not enforce this — Tailwind keeps numeric utilities like `gap-2` resolving whether or not a scale exists, so both engines exist because neither covers the other's surface (templates vs. authored CSS).
- **Radius:** the spartan **nova** default — `--radius: 0.625rem` in `styles.css` — from which the preset derives four steps: `--radius-sm` at 0.6×, `--radius-md` at 0.8×, `--radius-lg` at 1× (equal to `--radius` itself), and `--radius-xl` at 1.4×. `--radius-sm` is real and in production use — `shell.layout.css` rounds the sidebar's active-item indicator with it — and previous text omitted it entirely. Corners are token-driven: generated components carry `rounded-lg` / `rounded-t-xl` / `rounded-sm`, which resolve through `--radius`, so one line in `styles.css` restyles every corner in the app. Avatars are the only fully round element (`--radius-full`). Gated by Stylelint's `scale-unlimited/declaration-strict-value` on `border-radius`.
- **Backgrounds:** flat solid fills. No gradients, no imagery, no texture — checked directly: zero `bg-gradient-*` / `bg-linear-*` / `bg-radial-*` utilities anywhere in the frontend, confirmed by a one-time grep, not a running gate. Stylelint's `scale-unlimited/declaration-strict-value` on `background` forbids a hardcoded value in authored CSS, but Stylelint scans `.css` files only — a `bg-gradient-*` utility class added to an Angular template tomorrow is invisible to it. This claim is a review rule with no exit code.
- **Type:** body text reaches 14px through the `text-sm` utility applied per element (78 uses), not through a root font size — there is no `font-size` declaration anywhere in `styles.css`, `app.css`, or `index.html`, and Tailwind's un-set base is 16px. `font-mono` (13 uses, developer-facing content) resolves to Tailwind 4's default mono stack, which includes Consolas — this is Tailwind's default, not a jig token, and the app supplies no override. Both are stated here as mechanisms rather than as a single "Body 14px" base, because no such base exists: setting one at the root would double-apply against the 78 existing `text-sm` call sites and render body text at 12.25px. Rebasing the type scale so a root size and `text-sm` cannot conflict is out of scope for this branch. Not independently gated beyond the general `no-literal-spacing`/Stylelint coverage above; there is no font-size or font-family gate today.
- **Copy:** terse and technical. Sentence case; identifiers stay lowercase (`users`, `jig`, `main`). No emoji (the passing-gate `✓` is the one sanctioned glyph). This is a review rule with no exit code, in the sense ADR 0009 uses the term — no tool checks tone or casing today.

### Vendored kit facts — recorded, not enforced

`frontend/libs/ui` is spartan's nova style, generated by `ng g @spartan-ng/cli:ui` and rebuilt byte-for-byte by every `npm run ui:style` (ADR 0010). Nothing below is a jig decision and nothing below is gated: the numbers describe what nova currently inlines, and the next style regeneration can change any of them without this document noticing. Do not read any line in this list as something CI would catch if it changed.

- **Spacing is spartan's half-step rhythm, not the app's 4px grid.** 77 half-step utilities are inlined across `libs/ui`: `px-2.5` (x18), `gap-1.5` (x14), `px-1.5` (x11), `py-1.5` (x8), `gap-0.5` (x8), `gap-2.5` (x5), `py-0.5` (x4), `py-2.5` (x3), `p-2.5` (x3), plus single uses of `pr-2.5`, `pb-2.5`, and `mx-3.5`. A primitive's internal padding can sit up to 2px off the app-authored grid. `jig/no-literal-spacing` explicitly excludes this tree; see ADR 0011 for why an eight-step scale absorbing these half-steps was rejected.
- **Control height is mostly, not uniformly, 32px.** `h-8` is the majority (17 uses) but `libs/ui` also ships `h-9` (x3), `h-7` (x6), `h-6` (x4), and `h-5` (x4). There is no single compact control height to point to.
- **Shadow reaches well past a hairline in overlays.** Eight components use `shadow-md` (6 uses) or `shadow-lg` (2 uses) — dialogs, popovers, and similar surfaces that need to read as above the page. This is a review rule with no exit code, in the ADR 0009 sense: no gate caps shadow depth, in `libs/ui` or in app-authored CSS. If `shadow-lg` starts showing up outside overlay-class components, that is a review conversation, not a build failure.
- **Motion has two legitimate bands, not one.** Control feedback — hover, press, focus — runs 120-150ms (`duration-100` x13, `duration-150` x2 in `libs/ui`); this is right where latency reads as sluggishness. Layout transitions run longer: the sidebar rail's collapse in `shell.layout.css` animates `grid-template-columns` over `.2s` (200ms), because a transition that changes the page's whole geometry needs to read as movement, not a snap — 150ms there reads as a jump-cut, and `frontend/e2e/shell.layout.spec.ts` asserts the animation is observable at that duration. `libs/ui` also ships durations outside both bands (`duration-200` x4, `duration-300` x1, `duration-1000` x1) that belong to specific components (a toast auto-dismiss, a progress indicator) rather than to either band as a rule. The 120-150ms and 200ms figures are review rules with no exit code — no gate caps a `duration-*` utility or a CSS `transition`, in `libs/ui` or in app-authored CSS.
- **Looping and repeating motion exists, deliberately.** `animate-spin` (x2, loading indicators), `animate-pulse` (skeleton loading), `animate-caret-blink` (text cursor), and `animate-indeterminate` (progress bar with unknown completion) all ship in `libs/ui`. These are not bounces added for polish; each communicates an in-progress state that has no natural end point, which is precisely when a loop is the right primitive. Scoped to `libs/ui` — no app-authored CSS adds a loop, and no gate would stop one from being added.
- **Borders and hairlines still hold as observed practice.** 1px hairlines are pervasive across both app-authored and vendored surfaces. This is a review rule, not a gate — the same Stylelint coverage above catches a literal `border-color`, but nothing checks border *width*.

## Smells that mean the pattern is breaking

- A literal hex or px in a component instead of a `styles.css` token.
- Nested flex containers doing a job one `grid-template-columns` or `grid-template-areas` would state in a single readable line.
- A hand-rolled control that duplicates a spartan helm component.
- Editing the `jig-design` skill's `css/*` to change how the *app* looks (edit `styles.css` — the skill is downstream).
- A prototype's React bundle wired into a production path.
- Rounded corners, gradients, a second accent color, or a roomier app-authored control scale — the app-authored rules above are a gate, not a default. The vendored-kit facts are recorded, not enforced; do not treat them as a gate that does not exist.
