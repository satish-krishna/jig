# DR0001 — Layer dependency violation

> Engine: `tools/analyzers/Jig.Analyzers/LayerDependencyAnalyzer.cs`. Ruleset: `tools/analyzers/Jig.Analyzers/ArchLayers.txt`. Decision: [ADR 0009](../../../.bob/adr/0009-architecture-rules-are-compiler-errors.md).

## What it forbids

Code in one layer naming a type that lives in a layer the map forbids it to depend on. The map is `ArchLayers.txt`, and today it reads:

    *.Domain          -> *.Application
    *.Domain          -> *.Infrastructure
    *.Application     -> *.Infrastructure
    *.Api             -> *.Infrastructure

`*` matches exactly one namespace segment, the product prefix, so `*.Api` covers `Jig.Api` and `Jig.Api.Users` and does not cover `Microsoft.EntityFrameworkCore.Infrastructure`.

## Why

Layer dependency is a property of a graph, not of a file. .NET flows transitive project references straight through, so a forbidden type can be in scope through an intermediate project while every file a text search reads is innocent. Roslyn has already resolved that graph; this analyzer reads it rather than rebuilding it.

The rule is `NotConfigurable`. `.editorconfig` severity, `<NoWarn>`, and `#pragma warning disable` all fail against it. A dial you can turn up is a dial you can turn down, and a rule that has been switched off cannot report that it has been switched off.

## Fix the dependency, not the map

This is the whole point of the message, and the tempting wrong move is to edit `ArchLayers.txt` so the build goes green. That file is guarded by `tools/hooks/guard-ruleset.mjs` and changing it is treated as a law change, reviewed as one.

The right fix is almost always to route the dependency through the port that already exists.

    // Wrong: an endpoint reaching past the port into the adapter
    public sealed class GetUserEndpoint(JigDbContext db) { }

    // Right: the endpoint speaks the use-case layer, which speaks IUserRepository
    public sealed class GetUserEndpoint(UserService users) { }

If a rule here starts producing exceptions that are genuinely legitimate, that is evidence the rule is wrong, and it should be removed in a reviewed diff rather than dialed down.

## Known blind spots

It reports where code **names** a type whose namespace is forbidden, including names buried mid-chain (`Jig.Infrastructure.JigDbContext.Label.ToString()`) and types arriving through inference (`var db = Bridge.Get();`). It does not chase a type that is never named, such as `bridge.Db.Users.Count` where `Db`'s declaring type sits in a permitted layer and only its return type is forbidden.

A single violation can report more than once when several links in one member-access chain each name a forbidden type. That duplication is deliberate: two errors are a nuisance where a missed one is a lie.

`*.Infrastructure` matches any two-segment namespace ending in `Infrastructure`, so a third-party package named `Vendor.Infrastructure` would trip it. Nothing in the current dependency set does.

`Program.cs` uses top-level statements, so its generated class sits in the global namespace, which no `*.Api` pattern matches. The composition root exempts itself structurally rather than through a skip-list. Wrapping `Program.cs` in `namespace Jig.Api;` would fail the build on legitimate wiring.
