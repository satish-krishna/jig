# no-unknown-primitive

> Engine: `tools/lint/rules/no-unknown-primitive.ts`. Vocabulary: `tools/lint/vocabulary.ts`.

## What it forbids

An `hlm`-shaped attribute directive (`hlmFoo`) or element (`hlm-foo`) that matches no primitive actually installed in `libs/ui`, checked in the form it was written. Anything that looks like an attempt at a primitive — matching `^hlm[A-Z]` for an attribute or `^hlm-` for an element — is checked; a name that merely happens to start with those characters by coincidence is not exempted, because in practice nothing in this codebase does.

## Why

`libs/ui` is generated by `npm run ui:style` from whichever spartan style is active, and `showcase/component-api.generated.ts` is the live record of exactly what it installed. A hand-typed primitive name can drift from that record two ways: a plain misspelling (`hlmButton` for `hlmBtn`), or the right name written in the wrong syntactic form (an element-only primitive written as an attribute, or vice versa). Both compile — Angular does not fail a build over an unrecognized attribute on a native element — so nothing catches them short of a human noticing the control did not get styled. This rule reads the same generated data the freshness gate already trusts, so there is no second source of truth to fall out of sync.

### The jig-specific correction

A reader coming from the angular-jig reference rule set will expect a primitive to be "either an attribute directive or an element, never both." That claim is false under jig's nova style and would reject correct code here: 138 of 318 installed selectors declare **both** forms on one primitive, for example `[hlmAccordion], hlm-accordion`, and some are element-qualified, for example `button[hlmAlertDialogAction]`. The rule therefore derives both the attribute set and the element set from the same generated data via `attributeSelectors()` and `elementSelectors()` in `tools/lint/vocabulary.ts`, and does not assume the two sets are disjoint. `<div hlmAccordion>` and `<hlm-accordion>` are both accepted, because both forms are genuinely declared.

The wrong-form check survives this correction: `hlmSelectTrigger` written as an attribute (`<div hlmSelectTrigger>`) still fails when only the element form `hlm-select-trigger` is declared, because it is absent from the attribute set regardless of how many primitives declare both forms.

## Accepted form

    <button hlmBtn>x</button>
    <hlm-accordion></hlm-accordion>
    <div hlmAccordion></div>

## Rejected form

    <button hlmButton>x</button>        <!-- misspelled: hlmBtn is the real name -->
    <hlm-nonsense></hlm-nonsense>        <!-- no such primitive in any form -->
    <div hlmSelectTrigger></div>         <!-- right name, wrong form: only hlm-select-trigger exists -->

## Known blind spots

- It matches on name shape (`^hlm[A-Z]`, `^hlm-`), not on a registry of "things that claim to be directives." A three-letter coincidence starting with `hlm` followed by an uppercase letter would be flagged even if it were never meant as a primitive; nothing in this codebase does that today.
- Like `no-raw-control`, it reads static attribute and bound-input names only, so a primitive name assembled at runtime (for example, interpolated into `[attr.class]`) is invisible to it.
- It does not check whether an attribute directive is applied to a compatible native element — `button[hlmAlertDialogAction]` used on a `<div>` would satisfy this rule (the name is a real primitive, written in the right form) even though the qualifier restricts it to `<button>`. That compatibility check lives in the vocabulary's own test suite (`tools/lint/vocabulary.test.ts`), not in this rule.
