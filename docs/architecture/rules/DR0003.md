# DR0003 — Architecture ruleset line is malformed

> Engine: `tools/analyzers/Jig.Analyzers/LayerDependencyAnalyzer.cs`. Ruleset: `tools/analyzers/Jig.Analyzers/ArchLayers.txt`. Decision: [ADR 0009](../../../.bob/adr/0009-architecture-rules-are-compiler-errors.md).

## What it forbids

A non-blank, non-comment line in `ArchLayers.txt` that does not parse as `<from> -> <to>`. One diagnostic is reported per malformed line, naming the line number and its text, at `CompilationEnd`.

## Why

DR0002 fires only when *every* rule is gone. Before DR0003 existed, a line that failed to parse was skipped in silence, so `ArchLayers.txt` could lose exactly one rule to a dropped `>` or a stray `-` while `rules.Length > 0` kept DR0002 quiet and the build green. A typo could delete a law and nothing would say so.

A rule file is not prose. A line in it either is a rule or is a mistake, and the second one has to fail the build.

## Accepted form

    # comments and blank lines are fine
    *.Domain          -> *.Application
    *.Application     -> *.Infrastructure

The separator is `->`. Whitespace around it is free. Both sides are namespace patterns where `*` matches exactly one segment.

    Good: *.Api         -> *.Infrastructure
    Bad:  *.Api         -  *.Infrastructure     (no >)
    Bad:  *.Api         => *.Infrastructure     (wrong arrow)
    Bad:  *.Api            *.Infrastructure     (no separator)

The message names the line number and echoes the text, so the fix is usually visible without opening the file.

## Known blind spots

**It checks shape, not sense.** A line that parses is accepted, so `*.Nonsense -> *.Alsononsense` is a valid rule that will simply never match anything. A rule naming a layer that does not exist is indistinguishable from a rule that has not fired yet, and this analyzer cannot tell them apart.

**It cannot fire from a compilation it never joined.** Same hole as [DR0002](DR0002.md): unloading the analyzer silences both. See that document for why this is accepted rather than solved.
